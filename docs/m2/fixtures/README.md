# Complete wire examples — documentation only

These examples illustrate candidate `03_PREVIEW_AND_FRONTEND_CONTRACT.md` types. They are not responses from implemented preview endpoints. Core states and the wrong-anchor error were generated by real existing transitions with the explicit **unit-fixture-only** two-mission availability callback; training metadata/progress/access are projections of the proposed contract.

- START_RESPONSE.example.json: entire proposed HTTP200 start response, fresh demo core, Station Arrival active, empty Passport, no scientific validation claim.
- WRONG_ANCHOR_REQUEST.example.json: entire attempted fan placement after station completion/duct installation, expected session revision5.
- WRONG_ANCHOR_RESPONSE.example.json: entire proposed HTTP200 domain refusal with the unchanged revision5 state/checkpoint and the real core WRONG_ANCHOR message.
- UNAUTHORIZED_RESPONSE.example.json: entire proposed HTTP403 transport error, no snapshot leaked.

The opaque checkpoint fields are genuine example MAC encodings under the deliberately **public test-only key** `Buffer.alloc(32,7)` and prefix `microfire-m2-checkpoint-v1\0`; they are not credentials, grants or product signatures. No production/local-preview server may use that key. Fixtures still require real authorization, the correct configured secret/origin, runtime schemas and rules before any future server will accept them. Test clocks are fixed, so example access expiry is intentionally historical outside that test clock. Never report these examples as implemented E2E success.

Runtime acceptance tests must generate fresh fixtures through the actual API and private test key, not load these checkpoints as a bypass. Snapshot validity requires schema parsing plus MAC/scenario/lineage checks; a TypeScript example check alone is not that validation.
